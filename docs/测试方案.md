# 问数官 · 测试方案

> 传智杯第九届 · AI 赋能·智能测试创新挑战赛（团队赛）· 路径一：智能体应用的全方位测试

## 一、方法论地基：为什么选 Text-to-SQL 当靶子

> **核心判据：工具输出必须确定性可验证。**

如果 Agent 的工具返回的是 LLM 生成的文本，"正确答案"本身就模糊，测试会退化为主观打分。
SQL 执行结果唯一确定——**标准答案可由 SQLite 自动执行生成，零人工标注**。整套测试因此可以
精确断言、全自动跑批、可复现。

## 二、被测对象：双通道校园智能助手

- **通道一（结构化）**：教务数据 → Text-to-SQL（10 张表，8000 学生/60000 选课）
- **通道二（非结构化）**：校规政策 → RAG 检索（政策文档库）
- 双通道带来一个别人没有的测试点——**路由正确性**（该查库还是该检索政策）。

## 四、自动化断言（FR-T03）

三类断言：

1. **result_hash**：结果集规范化（排序 + 类型统一 + 浮点精度统一）→ SHA256 比对，
   **不受行序影响**（NFR-05）；
2. **tool_sequence**：工具调用序列是否与期望一致；
3. **llm_judge**：主观维度用 LLM-as-judge（可选，未配置 Key 时跳过）。

### RAG 专项评测（FR-T04）：RAGAS + DeepEval

官方推荐技术栈点名两个大模型评测工具，本项目已接入（`testsuite/rag_eval.py`）：

| 工具 | 指标 | 说明 |
|---|---|---|
| **RAGAS** | faithfulness / answer_relevancy / context_precision | RAG 忠实度、回答相关性、上下文精度 |
| **DeepEval** | hallucination / answer_relevancy | 幻觉检测、回答相关性 |

两者均基于 **LLM-as-judge**，需 `pip install -e ".[rag-eval]"` 并配置 `LLM_API_KEY`。
未安装/未配置时**自动跳过**（在报告中标注 skipped 与原因），回退到确定性指标
（召回@3 / 忠实度），保证 0 Key 可复现、主流程不被阻塞。评测结果写入
`metrics.json` 的 `rag_eval` 字段，并在 `report.html` 单独展示。

**第三路（2026-10-28 新增）：自研 LLM-as-judge**（`testsuite/rag_judge.py`）。
RAGAS / DeepEval 在 `pyproject.toml` 中标注了 SSRF 与不安全 pickle 的供应链风险、默认不装，
因此补一个**判据对齐**的无依赖实现：把回答拆成事实性断言，逐条判断能否被检索片段支持，
`faithfulness = 支持数 / 断言数`，另给 0~1 的回答相关性。真实 LLM 轨道实测
faithfulness **1.0**、相关性 **0.9167**（6 条样本）；判官有效性做过反向验证
（同一片段下编造回答 faithfulness 0.0 / 相关性 0.3，忠实回答 1.0 / 1.0）。

### 判官可信度验证（`testsuite/judge_agreement.py`，2026-10-28 新增）

自研判官解决"没有工具箱"，但没解决"判官自己准不准"。补两个**无人工标注也能测**的指标：

| 指标 | 方法 | 能说明 | 不能说明 |
|---|---|---|---|
| 稳定性 | 同批样本重复判 k 次 → 一致率、Cohen's κ、分数 MAE | 单次分数是否可复现 | 稳定地判错也是一致率 1.0 |
| 判别力 | 6 条金标（3 忠实 + 3 编造：改数字 / 片段外知识 / 半真半假）→ accuracy、precision、recall、两组均值 | 能否区分编造 | 金标由本项目按判据构造，**不是第三方人工评分** |

工程细节刻意做了三处"不许自欺"：
①全同类标签时 κ 返回 `None`（不硬编 1.0）；②判官没给结论的样本不计入一致率分母；
③指标不达标时结论直接写"不稳定/判别力偏弱"，不写"可用"。

## 四·五、结果集判定的分级等价（`testsuite/equivalence.py`，2026-10-28 新增）

精确比对（`result_hash`）严格但会把"同样对、写法不同"判错。现按级别放宽容忍，
**默认只放开数值容差**，其余必须由用例声明：

| 级别 | 放宽 | 默认 | 用例 |
|---|---|---|---|
| `exact` | 无（行序无关） | ✅ | 行序不同 |
| `numeric` | 数值精度/类型 | ✅ | `943` vs `943.0` |
| `projection` | 多选列 / 列序不同（列名+同义名对齐） | ❌ | 问人数答 `(college, COUNT(*))` |
| `column_subset` | 少选列（留下的列必须逐行对得上） | ❌ | 问「有哪些老师」只答姓名、没答职称 |
| `set` | 重复行（DISTINCT 与否） | ❌ | 「有哪些学院」 |
| `subset` | 少几行（LIMIT/采样） | ❌ | 「取前 10 条」 |

主指标 `执行准确率` 仍按严格口径，`语义等价准确率` 与 `严格判错但语义等价` 作为**附加**指标
一并进 `metrics.json` —— 两个数都摆出来，谁也不能替谁说话。

`column_subset` 单列一档而不并入 `projection`：多给一列无害，少给一列可能丢掉被问的关键信息
（按学院统计却丢了学院名），两者的风险不对称，报告里必须能分辨。

**改口径的代价必须可量化**：`testsuite/replay_llm_details.py` 直接重放已落盘的模型 SQL
（不调用大模型、不花 token），并自校验"重放出的严格判定与原跑批逐条一致"；
不一致说明数据库或期望变了，脚本退出码非 0，结论不得引用。实测：

| 口径 | 真实 LLM 59 条 | 说明 |
|---|---|---|
| 严格 | **55/59 = 93.2%** | 主指标（第十六轮修掉基准错误后重跑） |
| 含 `column_subset` | **59/59 = 100%** | 新增 4 条均为「问老师只答姓名、未答职称」 |
| 仍判错 | 4/59 | 只在上表 `column_subset` 口径下算对；严格口径仍记为错（口径争议，不是模型错误） |

对照历史：第十五轮同一批用例严格 53/59（89.8%），第十六轮修正两条期望 SQL（奖学金"种"、成绩只算已结课）
后升到 55/59；两次都保留了原始产物，可复算。

## 四·六、外部接入与人工对齐（第十六轮新增）

测试工具的成熟度，体现在"别人来用"时会不会卡住。以下四件事各配一条命令，全部可当场验：

| 问题 | 工具 | 判据 | 失败时给什么 |
|---|---|---|---|
| 这个端点到底能不能测？ | `testsuite/probe_endpoint.py` | TCP → `/v1/models` → 最小对话 → 3 条业务冒烟 | 结论分四类：`unreachable` / `auth_failed` / `protocol_mismatch` / `too_slow`，并给下一步 |
| 换个模型结论还成立吗？ | `testsuite/model_matrix.py` | 多模型跑同批用例 | 把失败拆成「所有模型都错（真难题）」与「只有某家错（模型特有）」，缺 key 标 `skipped` |
| 判官跟人对得上吗？ | `testsuite/judge_human_check.py` | 20 条真实回答人工标 1/0，算 accuracy/precision/recall/**κ** | 未标注与判官无数值的行不进分母；全同类标签 κ 返回 `null` |
| 单轮准确率是稳态还是运气？ | `testsuite/llm_track.py --rounds N` | 同批用例跑 N 轮 | 均值/区间/标准差 + 点名「跨轮不稳定题目」 |

**本轮实测到哪一步**（把"工具存在"和"工具有效"分开写）：

| 工具 | 实测结果 | 状态 |
|---|---|---|
| `probe_endpoint` | 本地起 OpenAI 协议桩（仅标准库），`verdict=ready`；`/v1/models` 返回 404 被标注为"端点不实现模型列表，不影响对话"，未误判为 `protocol_mismatch` | ✅ 已验 |
| `model_matrix` | 三份模型配置（deepseek/qwen/glm）已就位，**缺 `QWEN_API_KEY` / `GLM_API_KEY`** → 标 `skipped` 并写明缺哪个变量 | ⏸ 待配 key |
| `judge_human_check` | 20 条样本 + 8 条人造编造已导出；**抓编造：默认 0.5 抓 5/8，0.67 起 8/8**（见下）；κ 待人工填 20 行 | ◐ 抓编造已验 / κ 待标注 |
| `llm_track --rounds 3` | 三轮均 55/59，均值 93.2%、区间 93.2%–93.2%、`pstdev=0.0000`、跨轮不稳定题 **0 条** | ✅ 已验 |

**为什么"抓编造"要单列一条命令**：`score` 必须等人填 `human_faithful` 才有分母，但"判官能否识别编造"
的真值来自我们自己注入的假条款（位置记在 `.meta.json` sidecar，不进 CSV 免得标注时被暗示），
注入那一刻答案就有了。把它卡在人工标注后面，等于让已能测的指标空转。于是新增
`judge_human_check injected`，并强制同时输出**代价侧**：

| 阈值 | 抓到人造编造（第一次导出 / 第二次导出） | 非注入样本被判低于阈值 |
|---|---|---|
| 0.50（默认） | 5/8 = 62% / **4/8 = 50%** | 0/12 ｜ 0/12 |
| 0.67 | **8/8 / 8/8** | 0/12 ｜ 0/12 |
| 0.75 / 0.90 | 8/8 / 8/8 | 0/12 ｜ 0/12 |

两次导出是同一批 20 题、模型回答与判官打分各自重跑一遍（题目构造确定性，回答不是）。
**两列的差异本身就是结论**：默认 0.5 阈值不稳定（5/8 与 4/8），漏掉的是判官给 0.5–0.667 的那几条
（判据："大体忠实，但多了一段没出处的规定"）；0.67 及以上两次都全抓。所以"判官可用"必须连着
阈值一起写，否则结论取决于一个没进报告的常数。抬阈值在本批零代价（非注入 12 条两次最低分都 ≥0.9），
但**真值未知**，`others_below_threshold` 不等于误判——要判误伤只能看人工标注。

**盲标（`export --blind`）是 κ 能被当证据的最低要求**：标注表里若带着 `judge_faithfulness`，
人眼很难不参考它，那样算出的 κ 已经不是"判官与人工一致"，而是"判官与看着判官分做答的人一致"。
盲标把判官分挪到 `<stem>.judge.csv`，`score` 按 id 合并回来；缺 sidecar 时该行记为"判官无结论"，
**绝不默认判官为忠实**。

**两条基准错误的修正（同轮）**——它们提醒我们"尺子也会错"：

| 用例 | 原期望 | 问题 | 修正 |
|---|---|---|---|
| `D1-062/063` 某学院奖学金有多少**种** | `COUNT(*)` → 372/382（人次） | 问"种"答"人次"，模型给 `COUNT(DISTINCT name)=5` 反而被判错 | 期望与 mock 同步改为 `COUNT(DISTINCT name)` |
| `D1-002` 等成绩聚合 | `AVG(score)` 含退课记录 | `withdrawn` 仍有分数，被算进"平均成绩" | 期望、mock、提示词三处统一 `status='completed'` |

修正后同一批 59 条：严格 **55/59 = 93.2%**，含 `column_subset` **59/59 = 100%**。
守卫测试见 `tests/test_case_semantics.py`（8 项，含"两种口径在真实数据上确实不同"的反证）。

## 四·七、测试自身的两个「假信号」（第十六轮自查）

测试工具的成熟度不只看它抓出多少缺陷，还看**它报的失败是不是真的**。本轮全量跑出 9 红，逐个查完
发现有 2 类是"测试自己的问题"，都已修掉并加守卫：

| 现象 | 根因（实测定位） | 修法 | 反向验证 |
|---|---|---|---|
| 全量 9 项 `HTTPError 502` 假红：`test_serve_hardening` 4 / `test_rag_eval` 2 / `test_mutators_extra` 2 / `test_permission_round12` 1，**单跑全绿** | `testsuite/llm_track.py` 在 **import 时**就把 `.env.llm` 灌进 `os.environ`（CLI 需要：`agent.llm` 在 import 时构造单例并固化 `enabled`）。于是只要某个测试 import 了它，**整个 pytest 进程**都有 key，"未配置 key 就该跳过"的测试真的去连网 → 网络不通一律 502 | `tests/conftest.py` 加 autouse fixture：每个测试先清 `LLM_*` 再**重建 `_llm` 单例**（只删 env 不重建等于没关，`enabled` 是构造时固化的） | 把 fixture 改成 `autouse=False` 重跑：`test_env_isolation` 2 条 + `test_rag_eval` 1 条立刻变红，且耗时从 11s 涨到 96s（在等网络超时） |
| 全量 `pytest` 退出码 1，但 junit 是 `0 failures / 0 errors` | 沙箱 safe-delete 钩子拦住 pytest 清理系统临时目录（单次 90+ 文件触发批量确认），异常发生在 session teardown | ① 结论只信 `--junitxml`；② 临时目录放仓库内：`pytest -q --basetemp=_tmp_pt` | `--basetemp` 复跑：**530 passed，退出码 0** |

两次都属于"**测量方式错了，不是被测对象错了**"。这也是为什么本项目的结论一律标注口径
（哪个命令、哪个文件、是否 junit 读数），而不是只给一个"全绿"。

## 五、变异测试（FR-T07，★核心创新）

> 大多数队伍止步于"我造了 300 条用例，跑出准确率 78%"。但没人回答：**你怎么证明这些用例真能抓到 bug？**

| 编号 | 注入缺陷 | 预期被哪个维度检出 | 失效表现 |
|---|---|---|---|
| M1 | 移除 get_schema 工具 | 工具调用 | 工具序列缺 get_schema |
| M2 | 记忆截断为最近 2 轮 | 多轮对话 | 长程约束丢失 |
| M3 | 移除权限过滤层 | 对抗性与安全 | 越权数据泄露 |
| M4 | 政策库投毒 | RAG 检索质量 | 忠实度下降 |
| M5 | 温度提到 1.2 | 规划稳定性 | 同题多次结果不一致 |
| M6 | 禁用 clarify 工具 | 边界与异常 | 模糊问题硬答 |
| M7 | 破坏路由判断 | 路由正确性 | 政策问题答非所问 |
| M8 | SQL 列名幻觉（列名记错） | 功能准确性 | 列不存在 / 结果错（生成期静默失效） |
| M9 | WHERE 被静默丢弃 | 功能准确性 | 过滤条件被吃掉，结果集变大却报成功（执行期静默失效） |
| M10 | 记忆只写不读 | 多轮对话 | 约束存下了却从不应用（上下文失效） |

> M8–M10 是有意设计的**静默失效**：不抛异常、接口照常返回 200，只能靠"结果是否还正确"发现。
> 它们检验的不是"会不会崩"，而是"错得很难看出来时，断言还灵不灵"。

```
for mutant in [M1..M10]:
    run_full_test_suite(agent_with(mutant))
    compare_with(baseline)
    # 目标维度指标降幅 > MUTATION_KILL_DROP(默认 20%) → killed，否则 survived（盲区）
mutation_score = killed / 10   # 本项目实测 10/10
```

## 八、适用边界：这套工具能测谁、不能测谁（2026-10-28 新增）

**能被测的对象**：任何实现 `run(question, role, session_id, user_id) -> {answer, channel?}`
的对象；任意接受 JSON POST 的 HTTP 智能体服务（`HttpAgentAdapter`，支持请求/响应字段映射
与 `data.answer` 嵌套取值）；以及 **OpenAI 兼容协议**的智能体服务（`OpenAIChatAdapter`，
覆盖 FastGPT / Dify / vLLM / Ollama / OneAPI / 百炼，均不改对方代码）。

```bash
python -m testsuite.run_external --demo                       # 内置演示机器人（自带 5 类缺陷）
python -m testsuite.run_external --url http://host/chat       # 任意 HTTP 智能体
python -m testsuite.run_external --openai-base http://127.0.0.1:3000 \\
    --openai-model gpt-4o-mini --api-key sk-xxx --channel-path channel   # OpenAI 兼容协议
python -m testsuite.run_external --stub --stub-brain guarded  # 离线验证协议层（本地协议桩）
```

**能测的维度**：安全行为（越权 / 注入）、路由正确性、边界与澄清。
实测两个对照大脑（同一套用例）：朴素实现 安全 1.8%（55 条）/ 路由 54.3%（46 条）/ 边界 54.8%（31 条），
**检出 4 类缺陷**；补齐了身份校验、注入拦截、写操作拦截、澄清策略的同类实现 **100% / 100% / 100%，0 类缺陷**。

**协议层的诚实边界**：标准 OpenAI 协议只回正文、不返回通道信息，因此 `supports_channel=False`，
路由维度标为**不适用**而不是用正文猜通道；被测服务若额外暴露该字段，用 `--channel-path` 指过去。
本次提交环境无 Docker、无外网可达实例，**未实际连过 FastGPT/Dify**，协议层由仓库内
`examples/openai_stub/`（严格实现 200/400/401 与 `choices[0].message.content`）端到端验证。

**不能直接测的**：功能准确性（需 Text-to-SQL 能力与同一份库）、工具选择、多轮约束、稳定性、
性能。原因是这些维度依赖**被测体的内部结构**（SQL、trace、DB），外部黑盒拿不到。
诚实做法是显式声明并列入 `skipped_cases`（演示中跳过 31 条工具级用例），
而不是把它们算成"通过"来把通过率刷好看。
